# Storefront Page Copy Deck

Last reviewed: 2026-08-03

This is implementation-ready editorial guidance for the public no-commerce GitHub Pages preview.
It does not authorize a commercial product launch. `Relic Screenshot` is the owner-selected public
product name; professional clearance and the remaining release gates are still open. Text in
square brackets is an internal instruction or missing owner input, not public copy.

Claims are governed by `content/claim-register.md`. When the register says **release-gated** or
**owner input**, the site must use the pending-state copy below or omit the claim.

## Voice and editorial rules

- Calm, direct, specific, and Windows-native.
- Prefer a concrete verb and outcome: “Copy a capture” rather than “supercharge your workflow.”
- Let real product media establish quality; do not narrate every control.
- Avoid “best,” “instant,” “perfect,” “seamless,” “effortless,” “military-grade,” “private by
  design,” “never,” and other unmeasured absolutes.
- Do not compare against or name a competitor in public copy.
- Do not use fake scarcity, crossed-out prices, savings percentages, customer counts, ratings,
  testimonials, company logos, or review badges.
- “One-time purchase” does not imply lifetime updates. “Local” does not imply that licensing,
  support, checkout, or the website never uses a network.

## Global publication state

Until the name, offer, provider, policies, and signed installer are approved:

- Primary CTA: **Explore the product**
- Secondary CTA: **Release status**
- Commerce status: **Commercial release in preparation**
- Download status: **Signed installer not yet available**
- Account label: **License help**, not “Log in”
- Do not render a clickable Buy or Download action.

After every release gate passes, replace these states with the exact approved purchase, signed
download, and order-management actions. No placeholder URL may silently become a production CTA.

## FAQ `/faq/`

1. **What can I capture?**

   The current application supports selected areas, windows, the current monitor, all monitors,
   timers, repeated areas, and text capture. Scrolling capture remains in release validation.

2. **What formats are supported?**

   Screenshots save as PNG or JPEG. Recording paths produce MP4 or convert a recording to GIF.
   Final codec and compatibility details will be published from the release candidate.

3. **Can I annotate a capture?**

   Yes. The editor includes arrows, lines, shapes, freehand marks, highlights, text, numbered
   steps, blur, pixelation, spotlight, crop, undo, and redo.

4. **Does text capture need the cloud?**

   The current OCR implementation uses Windows’ installed OCR language packs on the PC. Available
   languages depend on the packs installed in Windows.

5. **Does it upload screenshots or recordings?**

   No cloud upload or hosted share-link feature exists in the current application. The final
   privacy policy will distinguish local capture processing from licensing, support, checkout, and
   website processing.

6. **Where are captures stored?**

   Saved files go to the folder selected in settings. If recent history or clipboard workflows are
   enabled, the app also keeps bounded local backing files. Exact locations and deletion controls
   will be documented for the release.

7. **Can it start with Windows and stay in the tray?**

   The app includes a launch-at-sign-in preference and explicit tray-first lifetime behavior.
   These are still being validated from the stable installed path across updates and Windows
   session changes.

8. **Which Windows versions are supported?**

   The exact minimum and tested Windows versions are not final. The application is currently an
   x64 Windows desktop build; requirements will be published after the compatibility matrix passes.

9. **How does the trial work?**

   The current app implements a 14-day full-feature trial, then requires a valid license for
   capture and recording. Final public terms will be published before release.

10. **How many computers can use one license?**

    The device and activation policy is not final. The current offline key mechanism must not be
    described as enforcing a device limit.

11. **Are updates included?**

    The update entitlement is not final. Do not infer lifetime updates from a one-time purchase.

12. **Can I buy or download it now?**

    Not from this preview. Checkout and download remain unavailable until the offer, policies,
    provider journey, signed installer, and release validation are complete.

13. **How will purchase recovery and license transfers work?**

    The production order-management and recovery route is not configured. The app includes local
    activation/deactivation controls; complete provider instructions will be added after the flow
    is tested.

14. **What is the refund policy?**

    The refund policy is in preparation and will be shown before checkout opens.

15. **Can it capture every protected or elevated window?**

    No universal guarantee is possible. Windows security boundaries, UAC, DRM, and protected
    content can limit capture. Release support documentation will cover known cases.

## Privacy `/privacy/`

This page is a content specification, not a publishable privacy policy. A qualified policy owner
must approve the final language and effective date.

### Verified product data map to disclose

- User-selected screen pixels processed for capture.
- Optional cursor, click, and keystroke display during enabled recording workflows.
- Saved screenshots and recordings in a user-chosen folder.
- Bounded local image-history copies when enabled.
- Bounded local clipboard-backing files used by image/file clipboard workflows.
- Recording/conversion temporary files and cleanup/failure-preservation behavior.
- Local settings, including save path, shortcuts, capture/recording preferences, and last area.
- Local trial timestamps in a file and current-user registry value.
- A hashed value derived from Windows machine identity and current user for local license/trial
  binding.
- A locally stored license record protected at rest with Windows DPAPI for the current Windows
  user. This does not enforce a device/seat limit or protect against software running as that user.
- Privacy-redacted local error log; final retained fields and rotation require release review.
- Future licensing-provider requests only if online activation is approved and wired.

### Required policy sections

1. Publisher/controller identity and contact.
2. Scope and effective date/version.
3. Local capture, editing, OCR, recording, clipboard, history, and temporary-file processing.
4. Exact file/registry locations, retention, limits, controls, deletion, uninstall behavior, and
   cloud-synced-folder caveat.
5. Global hotkeys, screen capture, audio, cursor/click, and keystroke-overlay behavior.
6. Licensing/trial data and exact provider fields/endpoints if online activation ships.
7. Website, checkout, order management, support, email, hosting logs, cookies, and analytics.
8. Purposes/legal bases, processors, international transfers, retention, access/deletion rights,
   security practices, children, changes, and jurisdiction-specific disclosures as applicable.

Prohibited shortcuts:

- “We collect nothing.”
- “Nothing ever leaves your device.”
- “Anonymous.”
- “Encrypted” for `license.dat`.
- “GDPR compliant” or similar compliance conclusions without evidence and review.

## Content handoff checklist

Before a page changes from pending to production:

1. Update the applicable claim-register rows.
2. Update the selected product name in controlled content sources and run a repository-wide
   obsolete-public-name search while preserving legacy paths and historical records.
3. Insert approved owner/provider/legal values; never leave bracketed instructions in public HTML.
4. Use only real synthetic-data product media or clearly labeled concepts.
5. Confirm every CTA destination in provider test mode and then production.
6. Confirm no page collects license keys, payment data, screenshots, recordings, or support data
   without an approved secure workflow and policy.
7. Validate headings, link text, alt text, keyboard order, no-JavaScript behavior, mobile reflow,
   contrast, metadata, internal links, and unavailable states.
8. Cross-check the signed release manifest before publishing version, requirements, size, checksum,
   signing, download, or changelog facts.
